## Recommended approval path

Avoid asking the user to approve every routine POC finance choice. The Finance Controller agent defines project policy and a **v1 supported transaction envelope**, using common-practice, bounded POC defaults where safe. The envelope should state the supported customer/account types, jurisdictions, currencies, ship methods, and offer cases. Narrow or exclude cases (for example, currency conversion or promotional offers) only when needed to keep the demo useful and honest. Excluded or indeterminate cases must fail closed; they must not be silently treated as zero, converted using a sample rate, or presented as a completed order. For real production use, an authorized human Finance/Controller owner must validate jurisdiction-specific, accounting, legal, or organizational requirements before financially final orders are enabled.

For every financial component required by that envelope, record the project rule, its POC/production scope, source or authority, precedence, effective date where applicable, rounding, zero-versus-omitted behavior, and audit evidence. The Finance Controller agent decides project policy; do not imply this is approval by an external human Finance/Controller owner. If a component is not needed for an explicitly supported case, record why and what the API must return for cases outside that scope. Engineering then verifies source access, implementability, and persisted-value behavior; technical feasibility is not policy approval.

Recommended sequence:

1. The Finance Controller agent defines project policy for the supported envelope and the price, tax, freight, currency, rounding, and audit rules, using common-practice POC defaults where safe. For production, an authorized human Finance/Controller owner validates external financial authorities, effective dates, and compliance/accounting treatment; include representative worked examples and boundary cases.
2. The Project Owner confirms the envelope is useful for the initial internal workflow. If it is not, retain the current product-only transient draft and revise the proposed scope; do not relabel it as a quote or order.
3. API, Database, Security/Identity, and deployment owners verify source access, authorization, persistence, retry, and recovery requirements against the approved envelope. A gap returns to Finance or the relevant owner; it does not get filled with a database default or an inferred rule.

**Acceptance for production AW-033:** Every financial value required for every in-envelope transaction has a Finance-approved authority and deterministic handling rule; zero is distinguishable from unknown; out-of-envelope and unavailable-source cases have explicit blocking behavior; and Finance/Controller records owner, effective date, and evidence. Until then, financially final production orders remain blocked. For POC demo behavior, `Product.ListPrice` is the demo/list price, displayed in USD without conversion; a verified zero displays `$0.00`; the uniform 7.5% demonstration rate applies to aggregate merchandise subtotal, excluding freight and offer discounts, and tax is rounded once to two decimals midpoint-away-from-zero. A known zero subtotal displays `$0.00` demo tax. For a nonempty persisted demo order within the explicitly authorized `AdventureWorks2022_Test` scope, allow aggregate merchandise subtotal zero when every server-read line price is known; persist the known zero line prices, demo tax `$0.00`, and freight `$0.00` USD explicitly. Do not rely on a database default. If any line price is null/missing, reject before order persistence; if its source cannot be read, return an unavailable-source failure. Neither case may be converted to zero. With all required inputs known, the POC demo total is merchandise subtotal plus demo tax plus this explicit zero freight; do not call it a quote, payable amount, or production total. Missing/unavailable price data is labeled “Price unavailable” and suppresses dependent subtotal, tax, and total. Label monetary amounts as POC/demo USD. These bounded conventions do not claim the source field's stored currency, production currency policy, production tax authority, or production freight authority and do not authorize a route, writer, or financially final submission.

## Gate

Finance/Controller should record the source and rule approved for each applicable production component, including owner and effective date. POC zero-versus-unavailable presentation, demo tax behavior, and explicit zero-freight demo rule are bounded demonstration rules only; they do not establish production policy. No database default, seeded value, trigger, or inferred formula may be treated as production policy. Financially final production orders remain blocked.
