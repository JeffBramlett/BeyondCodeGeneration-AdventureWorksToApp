## Evidence and limits

- AdventureWorks `SpecialOffer.StartDate` and `EndDate` are SQL Server `datetime` values with no timezone identifier. Interpreting them as UTC is a product rule, not a schema fact.
- AW-038 read-only clone evidence found `SpecialOfferID = 1` (“No Discount”) linked to all 295 finished goods examined, and none of 209 non-finished products. These are sample-clone associations only; they do not establish orderability, eligibility, or policy. See [AdventureWorks P0 mapping](../data/adventureworks-p0-mapping.md).
- A `SpecialOfferProduct` link is necessary evidence of an offer/product association, but is not by itself proof that the pair is a valid order-detail representation for a product.
- **Database Engineer verification, 2026-10-27:** The existing reader-only check found `StartDate`/`EndDate` are non-null SQL `datetime` (precision 3), with descriptions “Discount start date” and “Discount end date” and no visible defaults. No metadata or repository evidence establishes or refutes a historical UTC convention; the sample dates are not used to infer one. At `2026-10-27T18:37:43Z`, zero of 16 offers were date-eligible, zero had a feasible positive `smallint` quantity, and zero of 504 products had an eligible linked pair. Offer 1 ended `2014-11-30 00:00:00`, so its 295 finished-good links are not currently eligible. The reader could not see `SalesOrderDetail` metadata/FK rows; see the verification boundary in the mapping document.
- **Database Engineer verification, 2026-10-27:** With explicit Project Owner authorization, a read-only query using the clone-only test writer confirmed the composite `SalesOrderDetail (SpecialOfferID, ProductID)` foreign key to `SpecialOfferProduct (SpecialOfferID, ProductID)` exists, is enabled, and is trusted. All 295 existing Offer 1 product links satisfy the referenced key; 209 products have no Offer 1 link. Thus the persistence marker is supported for linked products at the pair-FK level only. The API now exposes this per-product fact separately; it does not authorize submission or make Offer 1 eligible.

## Scope and gate

The operational defaults and explicit application UTC mapping are approved. The API now implements a database-backed eligible-offers read using the timezone-less SQL `datetime` wall-clock fields as UTC, as selected by the Project Owner, and a pure evaluator tests the approved boundaries. This mapping is not a claim about historical source-system semantics. The full catalog is the lookup scope, but order writes remain blocked until a valid eligible offer/no-offer persistence representation is verified for each product and submission-time eligibility recheck is implemented and tested. These decisions do not block existing catalog or customer reads. Approval does not authorize database changes or production writes, does not settle price, tax, or freight authority/calculation requirements, and does not satisfy production authentication/authorization gates.

The 2026-10-27 clone check found no currently date- and quantity-eligible linked offer pair. The Project Owner separately approved Offer 1 as a conditional, persistence-only marker for a line with no selected promotion, including outside Offer 1's promotional date window. This does not make it an eligible offer. A separately authorized read-only metadata query confirmed the composite order-detail FK is enabled/trusted and all 295 existing Offer 1 links satisfy it; the other 209 products lack a link. The API's separate no-offer-persistence capability route reports this per product without exposing the marker. This does not enable order submission, validate other order fields, or make Offer 1 selectable or price-bearing.

If later evidence conflicts with this explicitly approved UTC application mapping, stop and return to the Project Owner rather than silently changing conversion behavior. If no valid no-offer pair exists for a product, block that order path and request separate product/design approval; do not invent a fallback or change the schema under this approval.
