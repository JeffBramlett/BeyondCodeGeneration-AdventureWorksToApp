## Persistence-Neutral Product Price Review

`Application/ProductListPriceReviewEvaluator.cs` compares an immutable snapshot previously reviewed by the server with a fresh server-read `Product.ListPrice` snapshot. Equal known decimal values, including zero, are `Current`; changed values, missing product IDs, and fresh null/unavailable prices are `ReviewRequired`. Invalid or unavailable previously reviewed snapshots, invalid IDs/prices, and duplicate IDs are `InvalidNotEligible`. Comparisons use decimal equality without rounding or conversion.

This helper is an in-process comparison only. Its snapshot is not a client DTO, security token, or mechanism for transporting or persisting review state across requests. The evaluator is not wired to a route or DI and does not provide end-to-end changed-price protection.

## Local POC Price Review Receipt Decision

The delegated local POC Project Owner adopts these price-review freshness and reconfirmation rules:

- A server-reviewed price receipt has a fixed 15-minute lifetime measured by the server. It is not sliding or extended by reads.
- After expiry, the user must obtain a fresh server price review and explicitly reconfirm before proceeding, even if all prices are unchanged. Any changed known price requires showing old and fresh POC/demo USD values and explicit reconfirmation of the new values. A subsequent change requires review/reconfirmation again.
- A known zero remains `$0.00` POC/demo USD. A missing/null or unavailable required price blocks review and suppresses dependent amounts; it is never coerced to zero. A transient source failure is distinguishable from a successfully read null/missing value.
- Any change to the complete draft invalidates its receipt. A receipt never authorizes an order; a future submission operation must independently re-read current prices and all other required terms.

The architecture recommendation for a future local-only implementation is a single-process in-memory store with a 32-byte cryptographically random opaque handle, HMAC-SHA-256 digest keyed by a process-random memory-only key, and binding to authenticated issuer + stable subject + the canonical full validated draft + exact server-read price snapshot. Restart invalidates every receipt and requires a fresh review. The local Development identity is per Windows account, not per browser, so receipts are scoped to that account across local browser sessions; do not describe them as browser-bound. Never log handles, digests, SID, draft contents, or price snapshots. Keep the receipt out of URLs and browser persistence.

Provisional implementation resource limits are 20 active receipts per subject, 500 total per process, 16 KiB canonical payload per receipt, and an 8 MiB aggregate canonical-payload budget. Sweep expired entries before capacity checks. Never evict unexpired receipts to make room; fail issuance explicitly and retryably at capacity. These are local POC engineering safeguards, not business policy or load-tested capacity claims. The byte-budget accounting must be defined consistently in implementation; the 500-entry cap also bounds per-object overhead.

This decision authorizes only private, unregistered, unit-tested application code after API/Architect review. It does **not** authorize a browser-callable endpoint, DI registration, persistence, a submit route, order DML, or any database work. Before route exposure, Security review is still required for the local identity's shared-per-Windows-user scope, bearer-handle redaction, antiforgery token/header and middleware ordering, loopback-only routing, no-store responses, authorization, and capacity behavior. Any browser-callable issuance operation must not use GET and must require antiforgery; loopback and SameSite alone are insufficient. Receipt review state does not replace durable order idempotency or submission-time revalidation.

| --- | --- |

## Idempotency

The Project Owner accepted the recommended retry defaults on 2026-10-27. A retry of the same logical submission must return its original outcome or a safe status result, never create a duplicate, and never advise blind resubmission after an ambiguous timeout. Use a client-generated opaque idempotency key, scoped to the authenticated staff subject (issuer plus stable subject identifier), with a canonical request fingerprint:

- First use binds the key to that staff scope and canonical request fingerprint.
- Same key and same request returns the original committed confirmation or a safe in-progress/status result; it does not execute a second order. The approved minimal replay snapshot is the generated order ID/number; customer, bill-to, ship-to, and ship-method IDs; and ordered product ID, quantity, and selected offer ID or null. Include monetary values only where their authority is approved and they were persisted. Do not retain full rows or display-name snapshots.
- Same key with a different request is rejected as a conflict.
- Concurrent duplicates are serialized/deduplicated so at most one order is created; other requests receive the winning outcome or a safe in-progress result.
- Retain the idempotency outcome for at least the lifetime of the recorded order, so an old retry cannot create a duplicate after a short cache expires.
- Retain the replay outcome while the order remains available, including archive. For permanent deletion, retain a minimal protected tombstone (scope, key digest, fingerprint) for 30 days, then purge, subject to Data Retention/Privacy approval before implementing deletion retention.
- The winning key claim, order header/details, trigger effects, and committed result must have atomic/durable semantics. An in-memory cache alone cannot satisfy restart-safe retry behavior.

The Project Owner accepted the v1 canonical fingerprint semantics recorded in [ADR-001](../architecture/decisions/ADR-001-idempotency-storage.md). A pure canonicalizer and test vectors are implemented; they are not called by a route and do not provide durable idempotency. The Project Owner conditionally approved an application-owned database on the same SQL Server instance as AdventureWorks; local metadata inspection confirmed both local databases share one instance and a read-only transaction can access metadata in both. This does not verify production topology, HA/failover, coordinated backup/restore or RPO/RTO. DBA/deployment-platform approval remains required for those items, ownership and least-privilege grants.

Approved in-progress message: “This order is still being processed. Check this submission again; do not start a new order.” Approved ambiguous-timeout message: “We couldn’t confirm whether this order was recorded. Check this same submission to get its result. Do not start a new order.” The UI provides an explicit “Check submission” action that reuses the unchanged request and original key; no automatic new key or new order is created.

The 30-day post-deletion tombstone was selected by the Project Owner, but implementing deletion retention requires Data Retention/Privacy approval of tombstone fields, access, and purge behavior. Key/digest protection and atomic participation with order writes also remain technical/security approvals. A separate service/database on another server cannot meet atomic replay without a separately approved distributed-transaction or reconciliation design. Accepted decisions and the pure helper authorize no order route, database writer, or persistence changes.

## Persistence-Neutral Idempotency Outcome Slice

This software-only AW-017 preparation slice is implemented as described below. It defines observable outcome classification and replay-snapshot fidelity; it does not define or implement a SQL schema, ledger store, route, writer, or transaction. The next safe slice is the private receipt/preflight handoff above.

### Accepted behavior

- An absent claim is classified as `NewAttemptEligible` only; it is not proof that the caller won a durable key claim and must not itself authorize order creation.
- A committed claim whose stored fingerprint equals the canonical fingerprint of the incoming validated logical request is classified as `ReplayCommitted`. Return the original saved confirmation without recalculating it or executing a second order.
- A claim with the same staff-scoped idempotency key and a different fingerprint is classified as `Conflict`. Never return another request's confirmation or proceed as a new order under that key.
- An explicitly observable processing claim may be classified as `InProgress` and use the already-approved in-progress message. This observation is optional; the product contract does not require persistence to expose a separately committed pending claim. Do not invent a pending row that weakens atomicity.
- A result that cannot be established after an ambiguous timeout remains `Ambiguous`; the client uses the already-approved “Check submission” interaction with the original request/key. It must not be reclassified as new or cause a new key to be generated automatically.

For concurrent requests with the same scoped key, the durable persistence boundary serializes the claim. If the competing transaction commits, the observer returns the committed replay for a matching fingerprint or conflict for a mismatch. If it rolls back, the observer may attempt the atomic claim. If bounded waiting expires or the commit result cannot be established, classify the result as `Ambiguous`; do not infer `NewAttemptEligible` from a timeout.

### Replay snapshot fidelity

The saved/replayed confirmation contains the generated order ID and number; customer, bill-to, ship-to, and ship-method IDs; and line order with product ID, quantity, and selected offer ID or `null`. Preserve line order. Treat omitted offer and JSON `null` as the same no-promotion intent, consistent with the accepted canonicalization. Include monetary values only when the corresponding values were persisted under the approved scope; do not calculate new values during replay. Do not retain full database rows, display names, raw idempotency keys, or a numeric status as business meaning.

### Acceptance criteria

- Focused pure tests classify absent, matching committed, fingerprint-mismatch, in-progress, and ambiguous observations to the outcomes above.
- Replay tests return the saved confirmation unchanged, including original line order, offer nulls, and any persisted financial fields; they prove no second order execution in the test harness only.
- The classifier receives an observation already resolved for the authenticated issuer + stable subject + opaque key scope. Scope lookup/enforcement is outside the helper; an unscoped observation is not safe to replay.
- Validated request fingerprints and stored claim fingerprints are required inputs. Compare the canonical lowercase SHA-256 hex values with ordinal semantics (or equivalent digest-byte comparison); do not use culture-sensitive or implicit case-insensitive comparison.
- `CommittedMatching` requires a non-null saved confirmation snapshot. A malformed fingerprint or a committed match without its snapshot must fail closed as invalid state; it must not be reclassified as absent, new-attempt-eligible, or a successful replay. The precise API error mapping remains for the eventual contract decision.
- Replay snapshots are immutable at the classifier boundary: their ordered lines cannot be mutated after construction or while returning a replay. Cover multiple-line order preservation, nullable offers, and any optional persisted-money fields without recalculation.
- The default replay snapshot need not include financial fields. Include them only if the POC needs those persisted values and their exact representation has been approved; do not create or recalculate amounts in this slice.
- The fake/decision helper has no SQL connection, persistence dependency, route, DI writer registration, or database access.
- Tests and documentation explicitly state that fake-backed behavior does **not** prove durable claim storage, uniqueness under concurrency, atomicity with order writes, restart safety, or crash/timeout recovery.

The software-only types are `Contracts/OrderReplaySnapshot.cs` (`OrderReplaySnapshot` and ordered `OrderReplayLine`) and `Application/IdempotencyOutcomeClassifier.cs`. Fingerprints are validated as exactly 64 lowercase hexadecimal characters and compared ordinally. `ProcessingObservable` is an input observation only, requires its valid stored fingerprint, and mismatches classify as `Conflict`; this slice has no processing-state producer. Malformed observations classify as `InvalidState`. The snapshot copies its lines into a read-only collection and contains no financial fields, so replay returns persisted identifiers and lines without recalculation. Boundary tests verify the new types have no persistence/web dependencies or DI registration, no order writer is introduced, and `POST /api/orders` remains absent. These fake/pure tests do not establish durable storage, concurrency, atomicity, restart safety, or crash/timeout recovery.

### Architecture and security boundaries

The Project Architect recommends `InProgress` be an optional observation, not a required durable state. The accepted atomic transaction may expose no committed pending row: competing requests can wait for commit/rollback, then replay/conflict or attempt the claim. A pure classifier may represent `ProcessingObservable`, but a persistence implementation may never produce that observation. Do not introduce a separately committed pending row without an explicit durable recovery design and approval. Security must still approve raw-key handling and digest/custody before persistent storage is designed.
