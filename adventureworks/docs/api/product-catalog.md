# Product Catalog Read API

The API contract is defined by `GET /api/products`, `GET /api/products/{productId}`, `GET /api/products/{productId}/offers`, `GET /api/products/{productId}/eligible-offers?quantity=N`, and `GET /api/products/{productId}/no-offer-persistence`.

Product search accepts `page` (1-10,000, default 1), `pageSize` (1-100, default 25), optional `search` (up to 100 characters), `sortBy` (`productId`, `name`, or `productNumber`, default `name`), and `sortDirection` (`asc` or `desc`, default `asc`). Search matches product name or number. The response contains the selected page, `hasMore`, and only product ID, name, product number, subcategory name, and category name. Search results intentionally do not include prices.

Product detail returns the same product identity fields plus nullable `listPrice`, read directly from `Production.Product.ListPrice`. A numeric zero is a verified zero price; JSON `null` means the source value is null/unavailable and must not be treated as zero. SQL/read failures continue to fail closed with 503. The POC presents this field only as **POC/demo USD**, without conversion or offer discount; this is not a quote or production price authority. The isolated session-only draft may use the detail value for its approved demo subtotal/tax calculation. It must show “Price unavailable” and suppress dependent subtotal/tax when any required line price is null. No grand total, freight, order submission, or production financial behavior is implied.

The offers route returns offers linked to that product through `Sales.SpecialOfferProduct`. It does not assert current eligibility or expose discount, date, quantity, or price values. `Product.ListPrice` is returned only by product detail, under the explicitly approved POC/demo display boundary. No response indicates inventory availability.

The eligible-offers route covers the full product catalog as a lookup scope, but a product has a selectable offer only when at least one linked offer is eligible. It requires a positive product ID and `quantity` from 1 through 32767. It returns 400 for invalid input, 404 when the product does not exist, and 200 with only eligible offers when it exists. Each item is `{ "specialOfferId": int, "description": string, "discountPct": decimal }`, where `discountPct` is the decimal fraction from `Sales.SpecialOffer.DiscountPct` (e.g. `0.15` = 15%). Eligibility uses the API's current UTC instant, `StartDate <= instant < EndDate`, and inclusive `MinQty`/non-null `MaxQty` bounds. SQL `datetime` values have no timezone; the approved product policy maps their stored wall-clock fields explicitly to UTC without local-time conversion. This interpretation is policy approval, not evidence of the database's historical timezone convention. `discountPct` was added by Project Owner demo decision (2026-10-30), superseding the earlier rule that this route exposes no discount data, so the UI can preview discounted line amounts (`listPrice x (1 - discountPct) x quantity`). The preview is not authoritative: `POST /api/orders` re-reads and re-validates the offer and its discount server-side (see [order-submission.md](order-submission.md)). An empty array means no linked offer is eligible for that product and quantity at this instant; it does not mean that an order line without a promotion is valid.

The Project Owner conditionally approved `SpecialOfferID = 1` as an internal persistence-only marker for a no-promotion line, even outside that offer's date window. It is not an eligible/selectable offer and must not be used for discount or price calculation. This API does not return the marker or claim that any product can use it. A product's no-offer path remains blocked until its Offer 1 product link and order-detail pair validity are verified. Current clone evidence shows links for 295 finished goods and none for 209 non-finished products; the authorized reader did not independently verify the live order-detail FK. No schema change or arbitrary fallback is approved.

The no-offer-persistence route returns `{ "isSupported": true|false }` for an existing product, and 404 for a missing product. `true` means an Offer 1 product link exists and therefore satisfies the currently enabled/trusted composite order-detail foreign key; it is a narrow persistence-capability fact only. It does not mean Offer 1 is eligible, selectable, priced, or that an order may be submitted. The endpoint does not expose Offer 1's ID or description. In the verified clone, 295 products (all finished goods) have the link and 209 do not. At submission, the server must recheck the link and all other order conditions; unlinked products remain blocked for the no-promotion path.

The API uses `Microsoft.Data.SqlClient` when it can load a current-user DPAPI-encrypted password from `%LOCALAPPDATA%\AdventureWorks\test-reader.credential`. `ADVENTUREWORKS_READONLY_SQL_CREDENTIAL_FILE` may override the encrypted file path only; the API does not accept a plaintext connection string from the environment or appsettings. DPAPI decryption requires the API process to run as the Windows user who protected the file. The adapter constructs a fixed SQL-auth connection to `localhost`, database `AdventureWorks2022_Test`, login `AdventureWorksTestReader`; integrated authentication and other databases are rejected. Every opened connection verifies the current database/login, absence of `sysadmin` and `db_owner`, required server/database `CONNECT`, the approved table-level `SELECT` reads, and rejects effective mutation/administration permissions. SQL Server 2022 may report inherited `public` metadata permissions; the guard tolerates non-mutating inherited permissions while continuing to reject write/admin permissions. Any connection, identity, permission, or query failure returns a sanitized `503 Service Unavailable`. The sample `AdventureWorks2022` database is never an allowed target.

The query executor uses the existing product/customer planners without changing their SQL, binds values as typed parameters, and returns only the DTO fields in this contract. The offer route reports linked offer ID and description only; linkage is not current eligibility, and no price or availability is asserted. Keep the DPAPI-protected test credential outside the repository and expose it only to the API process through the current-user PowerShell launch context. Never print or commit the decrypted value.
