# ADR-001: Durable Order Idempotency Storage

- **Status:** Fingerprint and replay semantics accepted. Project Owner conditionally approved same-instance application-owned ledger storage and authorized development of a distinct clone-only POC API writer on 2026-10-28. The empty `AdventureWorksPocIdempotency` database and `Idempotency` schema are present with approved shell settings. Both paired backups and both disposable restores completed; full `DBCC CHECKDB` on each restore reported zero allocation and consistency errors. No ledger tables or runtime identity are provisioned, and no order route or committed DML is enabled. Committed POST remains hard-blocked pending the local gates in this ADR. These decisions do not authorize a weak-retry or in-memory-ledger route.
- **Date:** 2026-10-27
- **Scope:** Future order submission and durable idempotency design. The Project Owner separately authorized development of a distinct local POC writer for `AdventureWorks2022_Test`. This ADR does not authorize provisioning its login/credential, changing grants/schema, enabling a route, committed order DML, or any production write.

## Context

The accepted retry behavior requires a logical submission to be safe under retry and concurrency:

- An opaque idempotency key is scoped to the authenticated staff identity (issuer plus stable subject).
- The key is bound to a canonical request fingerprint.
- Same key and same request replays the original committed result or returns a safe in-progress/status result.
- Same key and a different request conflicts.
- Concurrent duplicates create at most one order.
- The result is retained at least as long as the order.
- The key claim, AdventureWorks order header/details, trigger effects, and replay outcome need durable atomic behavior. An in-memory cache is insufficient.

For the local POC, the opt-in Development identity is the Windows HTTP caller authenticated by Negotiate, not the API process identity. If a future idempotency implementation needs a stable subject, it must derive that subject from the authenticated caller identity under an explicitly approved contract; the current local staff claim alone does not establish an idempotency subject. Keep identity identifiers out of responses and routine logs. This local identity rule does not substitute for production OIDC.

AdventureWorks is a supplied reference schema. No application-owned idempotency table or schema is approved there. A distinct clone-only POC writer may now be developed under the explicit 2026-10-28 authorization, but no writer identity is provisioned and no order route exists. The AW-014 rollback-test writer remains separate and is not an API/runtime identity.

The accepted key scope is authenticated issuer plus stable subject. When a stable caller subject is explicitly implemented, the local Development identity must scope it to the Negotiate-authenticated Windows caller rather than the API process account. A local mutation route still needs antiforgery and the stated loopback boundary, and production OIDC remains separate.

## Recommendation

Use an **application-owned database on the same SQL Server instance** as the AdventureWorks order database for the idempotency ledger. Keep that schema separate from AdventureWorks. If deployment topology confirms both databases are on the same SQL Server instance and can participate in one local SQL transaction, one transaction can claim the staff-scoped key, create the order and trigger effects, reload the confirmation values, and persist the replay result atomically.

On 2026-10-28, the Project Owner conditionally approved this storage direction in principle and separately authorized development of a distinct POC writer pinned to the verified `AdventureWorks2022_Test` clone. The Database Engineer acts as local DBA for this POC. Writer development and DBA design/review may proceed; creating/provisioning the ledger, changing schema, granting permissions, provisioning a runtime identity, enabling a route, and performing committed order DML each remain subject to the applicable explicit approval and gates below. Committed POST remains blocked until all local gates are completed and recorded.

### Proposed atomic protocol — pending DBA/API/Security review

This is a logical protocol, not approved SQL, schema, grants, or execution authority.

1. Authenticate/authorize the operation and customer scope; validate antiforgery and bounded request shape. Derive staff scope on the server and compute the accepted v1 logical fingerprint. Never trust a client identity, amount, or review snapshot.
2. Use one clone-pinned connection, MARS disabled, one explicit `SqlTransaction`, and explicitly qualified application-ledger operations on the same instance. Do not use ambient transactions, a second connection, cross-database ownership chaining, or `TRUSTWORTHY` as a permission shortcut.
3. Serialize the protected scoped-key lookup/claim with a database-enforced unique boundary. **Candidate:** explicit SERIALIZABLE transaction with a supporting unique index and bounded lock waiting. DBA must freeze the locking/query plan and verify cross-database behavior; no database isolation setting change is proposed. RCSI alone does not protect multi-statement validation from concurrent changes. Targeted locking is an alternative only with equivalent demonstrated safety.
4. An existing committed matching claim returns its saved confirmation after current access authorization, without another order or recalculation. A mismatch conflicts. Check committed replay **before** requiring an unexpired receipt or fresh terms: expiry, restart, or price changes must not invalidate an already committed result. Receipt handles are not a new order intent. Any proposed transport metadata/fingerprint exclusion needs contract review; do not silently change v1 canonicalization.
5. Only a genuinely new atomic claim proceeds to trusted receipt validation and submission-time authoritative reads: customer/access, linked addresses, ship method, products/prices, selected offer links/date/quantity or no-offer marker support. Capture the evaluation instant consistently; hold appropriate read protection through commit so terms cannot change between validation and write. Receipt comparison alone is not SQL revalidation. Changed/expired review blocks new persistence and requires explicit reconfirmation; unavailable/null prices never become zero.
6. In that same transaction insert header/details using approved POC amounts, allow triggers, reload final generated/computed/trigger-maintained values, verify them, and save the minimal immutable replay result bound to the key/fingerprint. Commit only when all steps succeed. No order-only commit, post-commit ledger fill, or separately committed pending claim. The claim may remain unobservable until commit; `InProgress` is optional.
7. Roll back any failed attempt when possible. A known completed rollback permits a subsequent atomic attempt with the original key; lock/deadlock errors or cancellation do not by themselves establish commit outcome. A connection loss/timeout at commit stays ambiguous until a scoped durable lookup resolves it. Never infer absence from an unavailable lookup or create a fresh key automatically. Return success only after confirmed commit.

**Trigger exception gate:** `uspLogError` may write diagnostic `ErrorLog` after a trigger rollback. No diagnostic exception to the atomicity requirement is approved here. DBA must document the error transaction state and all surviving effects, and propose a safely induced clone-only test. Project Owner must decide whether diagnostic-only residue is acceptable; no order, history, person, sales-total, or replay business effect may escape atomic rollback. If business effects escape, stop and redesign; do not repair triggers, widen grants, or suppress the error under this handoff.

## Proposed Ledger Contract

The accepted fingerprint semantics are recorded below. Other ledger mechanics in this section are technical recommendations to validate during design, not implementation authorization:

### Accepted Fingerprint Canonicalization

The Project Owner accepted all four canonicalization decisions below on 2026-10-27. Version `v1` fingerprints the validated logical request, not raw JSON bytes. Canonicalize a fixed-schema object containing `customerId`, `billToAddressId`, `shipToAddressId`, `shipMethodId`, and `lines` in request order. Each line contains `productId`, `quantity`, and `offerId`; normalize both an omitted offer and JSON `null` to the same explicit null value because they represent the same no-promotion intent. A positive selected offer ID remains distinct. Reject duplicate product IDs before fingerprinting.

Serialize in a fixed property order with invariant integer formatting, UTF-8 encoding, no insignificant whitespace, and no locale-dependent representations. Include the canonicalization version in the fingerprint domain so future contract changes do not silently collide with earlier requests. The accepted digest is `SHA-256(UTF8("order-request:v1\n" + canonical-json))`. Persisting the digest alongside a staff-scoped key is not implemented; protecting the key/digest in storage remains for security review.

Line order is significant because it may affect persisted detail numbering and confirmation order. Do not sort lines during canonicalization. Exclude client JSON property order and whitespace, server-generated order/due timestamps, server-derived prices/taxes/freight, eligibility evaluation time, generated IDs, and review results. Any future client-controlled field added to the wire contract requires a new canonicalization review/version.

These canonicalization semantics are approved product/contract decisions. The pure canonicalizer and test vectors are implemented; they are not called by an order route and no fingerprint or key is persisted. The same-instance application-owned storage direction is conditional; an empty database/schema shell exists but no ledger structure or key/digest is persisted. Key/digest protection still requires Security review, and atomic transaction/recovery remains unproven. Timeout/replay behavior is accepted but not implemented. Approval does not authorize an order route, database writer, or persistence changes.

Illustrative canonical representation of a validated request (not a public DTO commitment):

```json
{
	"canonicalizationVersion": 1,
	"customerId": 42,
	"billToAddressId": 11,
	"shipToAddressId": 12,
	"shipMethodId": 2,
	"lines": [
		{ "productId": 7, "quantity": 3, "offerId": null },
		{ "productId": 8, "quantity": 1, "offerId": 5 }
	]
}
```

With the accepted semantics, omitted `offerId` and explicit JSON `null` canonicalize identically. Reordering object properties or adding JSON whitespace does not change the canonical bytes. Reordering the `lines` array does change them. The staff issuer/subject and opaque idempotency key scope the ledger uniqueness lookup separately; they are not duplicated in the request fingerprint.

## Ledger Contract Details

- Uniqueness key: authenticated issuer, stable subject, and opaque client key. Do not use display name or email as the identity key.
- Request binding: store the accepted versioned canonical fingerprint over the validated logical request, preserving request line order.
- Secret handling: do not log or return the raw idempotency key. Store a keyed digest or otherwise protect it from routine exposure; choose the mechanism during the security review.
- Same fingerprint: replay the persisted minimal committed confirmation.
- Different fingerprint for the same scope/key: return conflict; never run a second order.
- Concurrency: rely on a database-enforced uniqueness boundary and transaction/locking behavior so at most one request wins. A losing request reads the winner's committed outcome or receives a bounded in-progress result.
- Retention: retain the replay outcome at least for the recorded order's lifetime. Any longer retention, archival, and deletion policy requires the appropriate data-retention owner decision.
- Ambiguous timeout/commit: never create a new key automatically and never blindly repeat a write. The client retries with the same key to obtain the committed result or safely proceed after the first transaction rolled back.
- Replay payload: retain only the minimal confirmation data necessary to reproduce the original API response, under the same authorization and data-protection controls as the order.

## Accepted Replay Decisions and Retention Gate

The Project Owner accepted the following product-behavior recommendations on 2026-10-28. Data Retention/Privacy approval is required for tombstones only if permanent deletion/tombstone behavior is implemented:

- **Replay snapshot:** persist/replay the generated order ID and number; customer, bill-to, ship-to, and ship-method IDs; and line order with product ID, quantity, and selected offer ID or `null`. For this local POC, the decided POC money rules and existing calculator may supply the financial values; the Database Engineer acting as local DBA verified AdventureWorks order-amount SQL precision. These are POC rules, not production financial authority. Confirmation is **“Recorded”** only; it does not mean fulfillment acceptance, shipment, fulfillment, or reservation. Do not retain full database rows or display-name snapshots.
- **POC status storage:** omit the status column on insert and use the verified clone's default strictly as a storage placeholder. Do not present or interpret that default as an approved business/order status; the user-facing confirmation remains “Recorded.”
- **In progress:** show: “This order is still being processed. Check this submission again; do not start a new order.”
- **Ambiguous timeout:** show: “We couldn’t confirm whether this order was recorded. Check this same submission to get its result. Do not start a new order.”
- **Retry initiation:** provide an explicit “Check submission” action that repeats the original request with the original idempotency key. Do not automatically create a new key or start a new order after a timeout.
- **Permanent deletion:** if permanent deletion is implemented, remove the replay payload and retain only a minimal protected tombstone (scope, key digest, fingerprint) for 30 days, then purge it. The tombstone prevents old-key reuse/conflict bypass during that interval; after purge, deduplication is no longer guaranteed. Data Retention/Privacy must approve tombstone fields, access, duration, and purge before implementing that feature. If permanent deletion is absent, this approval does not block the local POC.
